Featured Finding

Hex-encoded IDOR — /addeditaddress

Real request captured with Burp Suite Repeater. A hex-encoded address ID could be incremented client-side to pull another user's saved address — with a reused, predictable CSRF token compounding the issue.

Repeater — addeditaddress.request
RequestBurp Suite
POST /addeditaddress HTTP/1.1
Host: target-app.internal
Cookie: session=8f2a...redacted
Content-Type: application/x-www-form-urlencoded

id=6b8b456e6b8b456e&
csrf_token=a1c9f0e2b7d4...
Response200 OK — awaiting send
// click "Send ▶" to replay with an incremented hex ID
SEVERITY: HIGH

Situation: The address-management endpoint accepted a hex-encoded record ID directly in the request body, with no server-side ownership check.

Task: Confirm whether ID manipulation could expose another user's saved address data.

Action: Intercepted the request in Burp, decoded the hex ID, incremented it by one, re-encoded it, and replayed the request through Repeater. Also flagged that the accompanying CSRF token did not rotate per-session.

Result: The response returned a different user's full saved address — confirmed and documented as a High-severity IDOR with a secondary CSRF weakness, written up with reproduction steps and remediation guidance (server-side ownership checks + per-request CSRF tokens).
